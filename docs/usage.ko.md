# 사용 가이드

[소개로 돌아가기](../README.md)

## 1. 어떤 프롬프트를 선택하나요?

새로운 결과물을 만들거나 계획을 추진하려면 [프로젝트 진행용](../prompts/project-management.ko.md)을 사용합니다.

이미 발생한 고객·제품·서비스·업무 문제의 원인을 조사하고 대응하려면 [문제 해결용](../prompts/issue-resolution.ko.md)을 사용합니다. 문제 해결용에도 기본 팀 운영 규칙이 들어 있으므로 프로젝트 진행용을 추가로 붙여 넣을 필요는 없습니다.

두 유형이 섞여 있다면 당장의 목표를 먼저 정하세요. 예를 들어 배송 오류를 해결한 후 주문 처리 시스템을 새로 만드는 경우, 문제 대응과 후속 구축 프로젝트를 연결하되 각각의 완료 기준과 기록을 구분할 수 있습니다.

## 2. 직급·직무·페르소나는 무엇이 다른가요?

| 항목 | 의미 | 예시 |
| --- | --- | --- |
| 직급 | 책임 범위 | 차장급 책임자 |
| 직무 | 실제로 담당할 일 | 고객 영향과 정상화 기준 정리 |
| 페르소나 | 일을 바라보는 전문 관점과 소통 성향 | 고객 관점을 우선 확인하고 근거로 제안 |
| 완료 책임 | 무엇으로 담당 업무를 끝낼지 | 영향 범위와 검증 가능한 정상화 기준 작성 |

페르소나는 서로 다른 관점을 확보하기 위한 장치입니다. 실제 경력이나 자격을 부여하는 장치가 아닙니다. 역할을 잘 연기했다는 사실이 분석의 정확성이나 조치 효과를 입증하지도 않습니다.

프로젝트 진행용에는 직무에 맞춰 페르소나를 배정하도록 명시했습니다. 문제 해결용에는 역할별 기본 업무 성향도 포함했습니다.

## 3. 시작하는 방법

1. 선택한 프롬프트 파일 전체를 복사합니다.
2. 사용할 AI 도구의 대화 또는 작업 지시 입력란에 붙여 넣습니다.
3. 파일 마지막의 업무 입력란을 작성하고 접근 가능한 자료를 첨부합니다.
4. 최초 응답에서 실제 기능·한도 확인, 팀 구성, 담당 범위와 계획을 확인합니다.

GitHub에서는 파일의 **Raw** 보기나 원문 복사 기능을 이용하면 Markdown 원문을 가져오기 편합니다. 실행할 프로그램이나 설치 명령은 없습니다.

업무를 입력할 때는 목적과 결과물, 제공 자료, 필수 조건, 실행 권한을 우선 작성하세요. 모르는 항목은 `미확인`으로 두면 됩니다.

사용 도구의 실제 기능과 상위 규칙은 계속 적용됩니다. 프롬프트에 병렬 실행을 적었다는 이유로 에이전트 생성 기능이나 실행 권한이 생기지는 않습니다.

## 4. 프로젝트 진행용 입력 예시

다음은 가상의 입력 예시입니다.

> **이번 업무**
>
> - 업무 목적: 신규 고객의 서비스 가입 과정을 쉽게 설명하기.
> - 원하는 결과물: 한국어 가입 안내문과 내부 담당자용 점검표.
> - 제공 자료: 현재 가입 절차 문서와 자주 묻는 질문 목록.
> - 필수 조건: 절차 누락 금지, 용어 통일, 실제 화면과 안내 순서 일치.
> - 일정·예산·환경 제약: 제공된 자료와 확인 가능한 화면을 기준으로 작업. 별도 비용 집행 금지.
> - 추가 요청: 확인할 수 없는 화면은 미검증으로 표시. 고객에게 발송하지 않고 초안과 점검 결과를 전달.

기대하는 작업 흐름은 자료 확인, 안내 구성 합의, 문안 제작과 절차 대조, 통합, 독립 검수입니다. 위 예시는 실제 수행 결과가 아닙니다.

## 5. 문제 해결용 입력 예시

다음은 가상의 입력 예시입니다.

> **이번 문제 해결 업무**
>
> - 문제 또는 고객 제보: 주문한 색상과 다른 제품이 배송됐다는 문의.
> - 발생 시점과 현재 상태: 최근 접수됐으며 추가 발생 여부는 미확인.
> - 영향을 받은 대상과 범위: 제공된 문의 기록에 포함된 주문. 전체 범위는 조사 필요.
> - 원하는 해결 결과: 발생 범위와 원인 조사, 대응안 및 재발 방지안 작성.
> - 제공 자료와 관련 기록: 개인정보를 제거한 문의 기록, 주문·출고 기록, 상품 옵션표.
> - 이미 수행한 조치와 결과: 미확인.
> - 필수 조건과 종료 기준: 주문 옵션과 출고 내역을 대조하고 확인된 사실과 가설 구분. 실제 조치·관찰이 없으면 해결 완료로 보고하지 않기.
> - 허용된 실행 권한: 제공 자료 분석과 대응 문안·조치 계획 작성.
> - 별도 승인이 필요한 행동: 고객 연락, 환불, 재배송, 주문 변경과 출고 중단.
> - 일정·예산·환경 제약: 실제 시스템 수정 권한 없음. 비용 집행 금지.
> - 추가 요청: 고객 실명과 연락처를 결과물에 포함하지 않기.

이 경우 AI가 직접 환불하거나 배송 문제를 실제 해결했다고 보고하면 안 됩니다. 자료 분석과 계획 작성의 완료, 실제 문제 해결의 완료를 구분해야 합니다.

## 6. 자유로운 회의와 만장일치의 범위

최초 계획, 주요 변경과 최종 완료는 전체 팀의 명시적 동의를 받습니다. 이미 합의한 계획 안의 세부 조사와 수정은 담당자가 진행합니다.

반대 의견이 나오면 근거와 영향을 확인하고 필요한 조사나 검증을 수행합니다. 합의가 되지 않았다는 사실을 숨기거나 침묵을 동의로 처리하지 않습니다.

문제 해결용의 긴급 조치는 사전에 승인된 범위와 지정 책임자에 한해 전체 회의를 기다리지 않고 실행할 수 있습니다. 긴급성 자체가 권한을 확대하지는 않습니다.

## 7. 실행 한도가 부족한 경우

- 역할 구분을 유지하고 작업 대기열을 운영합니다.
- 독립적으로 가능한 업무만 실제 한도 안에서 병렬로 수행합니다.
- 검수자 A와 B는 각각 별도 에이전트로 운영합니다. 필요하면 순차 실행합니다.
- 각각 최초 판정을 작성한 후 결과를 비교합니다.
- 별도 에이전트를 사용할 수 없으면 독립 검수 조건의 미충족을 알립니다.

여러 이름으로 답변하거나 역할별 문단을 작성한 것만으로 실제 여러 에이전트가 생성된 것은 아닙니다.

## 8. 결과물에서 확인할 내용

| 확인 대상 | 필요한 근거 |
| --- | --- |
| 요구사항 충족 | 요구사항 ID, 담당자, 산출물과 검증 결과 |
| 실제 실행 | 실행한 행동, 환경·버전과 확인 가능한 결과 |
| 수정 효과 | 수정 전후 비교와 재검증 |
| 독립 검수 | A와 B 각각의 최초 판정과 이후 비교 결과 |
| 완료 판정 | 필수 기준 충족, 미해결 사항과 검증 한계 |

문제 해결용에서는 다음 표현을 구분하세요.

| 해결 수준 | 의미 |
| --- | --- |
| 확산 방지 | 추가 피해를 줄이는 조치를 수행한 상태 |
| 임시 정상화 | 현재 증상이 완화되거나 정상 동작을 회복한 상태 |
| 근본 조치 완료 | 확인된 원인을 겨냥한 조치를 수행한 상태 |
| 재발 방지 검증 완료 | 합의한 범위와 관찰 조건에서 재발 방지 기준을 확인한 상태 |

원인이 미확정이거나 관찰 기간이 남아 있다면 이를 표시해야 합니다. 두 검수자가 동의했어도 검증 증거가 부족하면 완료 조건을 충족한 것이 아닙니다.

## 9. 문서의 범위

이 저장소에 포함된 문서는 대화에서 정리한 운영 프롬프트를 게시용 Markdown으로 구성한 것입니다. 프로젝트 진행용에는 후속으로 제안한 페르소나 배정 문단을 함께 반영했습니다.

특정 AI 도구나 실제 고객·제품 환경에서 업무 성과가 검증됐다는 뜻은 아닙니다. 사용하는 환경에서 실행 능력, 권한과 검증 범위를 먼저 확인해야 합니다.

고객·제품 문제의 성격에 따라 현장 점검, 담당 부서 또는 자격 있는 전문가의 실제 확인이 필요한 경우에는 그 의존 관계를 표시하고, 에이전트의 문서 검토만으로 대체했다고 보고하지 않습니다.
